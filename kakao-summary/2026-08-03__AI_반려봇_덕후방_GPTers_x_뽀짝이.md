## 인사이트·노하우

- **Hermes gateway FD(파일 디스크립터) 누수 (Errno 24) 진단 가이드** (지아코모 공유): 장시간 실행되는 Hermes gateway에서 `OSError: [Errno 24] Too many open files` 발생 시, 오류 발생 파일만 지우거나 `/reset`을 반복하기보다 **어떤 프로세스가 어떤 파일·소켓·SQLite 연결을 계속 물고 있는지부터 확인**해야 함.
  - 진단 순서: 실제 gateway PID 확인 → FD soft/hard limit 확인 → 열린 FD 수·반복 경로 확인 → 작업 전/중/후 baseline과 비교(복귀하면 정상 burst, 계단식 증가 후 미복귀면 실제 누수).
  - 실측 사례: macOS 환경에서 soft limit 256, `state.db` 102개·`state.db-wal` 101개로 FD 254/256까지 도달해 정지. 코드 수정 후 read-heavy 작업 30회 반복 시 DB/WAL/SHM 묶음이 27에서 더 늘지 않고 전체 FD도 75→73으로 안정화.
  - 핵심 구분: **통제 재시작**(응급 복구, 이미 열린 FD 회수) / **한도 상향**(장애까지의 시간만 늘리는 방어층, 근본 해결 아님) / **코드 수정**(종료된 worker 연결 회수, 근본 해결). "FD 한도를 4096으로 올리는 것만으로는 누수가 해결되지 않습니다. 연결이 계속 쌓이면 장애 시점만 늦어집니다."
  - 작성 시점(2026-08-03) 기준 공식 Issue는 열려있고 후보 PR들은 미병합 상태 — 재사용 시 최신 상태 재확인 필요.

- **카카오톡 봇 구현 시 계정 밴 위험**: 카톡 연동 봇("홀든")이 운영정책 위반으로 밴 처리됨. 다수가 사용 중인 **agent-messenger**로 연결된 봇이었고, agent-messenger는 **LOCO protocol** 기반이라 이런 방식은 "차단감수 해야" 하는 리스크가 있음(제보: P28, P29, P3). 스팸을 보내지 않아도 정책 위반으로 밴될 수 있음.

Hermes Errno 24 파일 디스크립터 누수 진단·복구 가이드 안내

여러분, 이번 자료는 장시간 실행되는 Hermes gateway에서 발생할 수 있는 다음 오류를 체계적으로 진단하고 해결하기 위한 가이드입니다.

OSError: [Errno 24] Too many open files


이 오류 메시지에 표시된 파일이 항상 누수의 원인은 아닙니다. 파일 디스크립터가 이미 고갈된 상태에서 다음 파일을 열려고 하다가 오류가 표면화됐을 수 있습니다.

따라서 오류가 발생한 파일만 삭제하거나 /reset을 반복하기보다, 어떤 프로세스가 어떤 파일·소켓·SQLite 연결을 계속 보유하고 있는지부터 확인해야 합니다.

이 자료에서 다루는 내용

1. 정상적인 일시적 FD 증가와 실제 FD 누수 구분
2. 실행 중인 gateway의 PID와 실제 FD 한도 확인
3. 파일·socket·pipe·SQLite DB/WAL/SHM 유형별 분석
4. 반복 표본을 통한 단조 증가와 기준선 복귀 여부 확인
5. macOS, Linux/WSL, Android Termux, Windows의 한도 모델 차이
6. 통제 재시작, FD 한도 상향, 코드 수정의 역할 구분
7. Hermes SessionDB 누수 원인과 안전한 lifecycle 수정 조건
8. 회귀 테스트와 24시간 안정성 검증 기준
9. 공식 Issue·PR·commit 반영 여부를 확인하는 방법

익명화된 실제 사례

한 macOS 계열 장시간 gateway에서는 다음 수치가 관찰됐습니다.

- soft limit: 256
- state.db: 102
- state.db-wal: 101
- 전체 FD: 254/256

수정 후 read-heavy operation을 30회 반복했을 때 DB/WAL/SHM 묶음은 27에서 더 증가하지 않았고, 전체 FD도 즉시 75, 10초 후 73으로 안정화됐습니다.

이 수치는 실제 측정값이지만, 운영 주체·사용자명·에이전트명·경로·채널·PID·profile은 모두 제거했습니다. 또한 하나의 사례일 뿐, 모든 macOS 또는 Hermes 환경의 기본값을 의미하지 않습니다.

핵심 구분

- 통제 재시작: 이미 열린 FD를 회수하는 응급 복구
- 한도 상향: 장애까지의 시간을 늘리는 방어층
- 코드 수정: 종료된 worker의 연결을 회수하는 근본 해결

FD 한도를 4096으로 올리는 것만으로는 누수가 해결되지 않습니다. 연결이 계속 쌓이면 장애 시점만 늦어집니다.

작은 실습

먼저 자신의 환경에서 다음 세 가지를 읽기 전용으로 확인해 보세요.

1. 실제 gateway PID
2. 해당 프로세스가 상속한 FD soft/hard limit
3. 현재 열린 FD 수와 가장 많이 반복된 경로

그다음 같은 작업을 여러 번 반복하면서 다음을 비교합니다.

작업 전 baseline
→ 작업 중 증가
→ 작업 종료 후 복귀 또는 plateau


작업이 끝난 뒤 FD가 기존 수준으로 돌아오면 정상 burst일 가능성이 높습니다. 반대로 반복할 때마다 계단식으로 증가하고 돌아오지 않으면 실제 누수를 의심해야 합니다.

실습 시 주의사항

- 증거를 수집하기 전에 프로세스를 재시작하지 않습니다.
- 정확한 gateway와 supervisor를 확인하지 않고 프로세스를 종료하지 않습니다.
- 여러 gateway가 있을 때 raw 프로세스를 추가로 실행하지 않습니다.
- 실행 중 프로세스의 실제 한도를 확인하지 않고 OS 기본값을 단정하지 않습니다.
