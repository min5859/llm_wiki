# GPTers AI 반려봇 덕후방 대화 정리 (2026-08-07)

## 인사이트·노하우

- **Hermes `/journey` 기능**: Hermes Desktop 채팅에 `/journey`(또는 `/learning`, `/memory-graph`)를 입력하면 그동안 쌓인 스킬·기억이 시간순으로 별자리 형태로 펼쳐지고 패널에서 바로 수정 가능. 터미널에서는 `hermes journey`. 텔레그램 등 메신저 채팅에는 없고 Desktop·CLI 전용. 로컬 설치 기준 CLI/TUI는 2026-06-30, Desktop 별자리 패널은 2026-07-02 커밋으로 추가됨.

- **devbox VM의 구조적 SPOF(단일장애점) 진단 및 해법** (P18↔P20 심층 대화):
  - 문제: devbox VM 안에서 devbox 자신을 재현하는 이미지를 만들기 때문에, VM이 죽으면 고칠 수단도 함께 사라지는 "자기 재현 순환" 구조. 게다가 VM 안에는 transcript(하네스 자가개선·devlog 원료), 전역명령, IAM, watchdog 등 프로젝트 관리 서비스가 모여 있어 push 한 번이 VM 전체에 적용됨.
  - 처음엔 카카오톡 챗봇 배포 경로(`dev(staging) → prod(vm) → iris-redroid(vm)`)도 devbox에 종속된 것으로 의심했으나, 실제로는 devbox보다 먼저 만들어져 완전히 독립적으로 동작한다고 정정됨.
  - 가장 큰 실질 위험은 **transcript**: 코드가 아니라 데이터이므로 git push 대상이 아닐 가능성이 높고, VM이 날아가면 자가개선 역사와 devlog 원료가 통째로 사라짐.
  - 제시된 개선안(비용 낮은 순):
    1. transcript를 VM 밖(GCS 버킷/별도 퍼시스턴트 디스크)으로 분리해 마운트만 하기
    2. ghcr 이미지를 노트북에서 `docker run`으로 띄우는 탈출 경로를 미리 한 번 실제로 검증해두기
    3. 배포가 건드리지 못하는 "직전 정상 상태로 롤백" 스크립트를 cloud-init/이미지 레벨에 별도로 구워두기
    4. repo를 "VM을 살리는 최소 부팅·SSH·Tailscale·롤백"과 "그 위의 개발 편의"로 분리해 엄격한 게이트를 다르게 적용
  - 참고 비유: 자기 자신을 배포하는 CI, 자기 컨트롤 플레인을 관리하는 쿠버네티스, 자기 시스템을 재구성하는 NixOS도 동일한 형태의 문제를 공유하며 해법도 대체로 위 네 가지 중 하나로 수렴한다는 코멘트.
  - 미해결로 남은 부분: partybot-iris-vm(redroid+Iris) 자체가 통째로 날아갔을 때, 호스트 재구축(redroid 커널 설정, binder, Iris 초기 구성) 절차가 문서·스크립트로 존재하는지는 확인되지 않음.

- **CLAUDE.md / status.md 컨텍스트 비대화 트러블슈팅**:
  - 원인: 파일을 여러 개로 나눠도 `@status.md` 같은 임포트로 자동 로드되면 이전과 비용이 동일함. 나눈 의미가 없어짐.
  - 핵심 원칙: 개수가 아니라 "상시 로드 vs 온디맨드" 분리가 핵심. 실측 사례 — 세션마다 무조건 로드되는 것은 CLAUDE.md+규칙파일(2KB)+메모리 인덱스(15KB)뿐이고, 실제 메모리 본문은 49개 파일 316KB. 인덱스가 전체의 5%만 노출.
  - transcript(무엇이 있었는가, 단조 증가)와 CLAUDE.md(어떻게 일하는가, 대체로 안정적)는 성질이 다르므로 섞으면 안 됨 — 규칙은 상시, 이력은 검색 가능하게 두고 필요할 때만 열람.
  - 3층 구조 권장: ①안 바뀌는 규칙(상시) ②무엇이 존재하는지 한 줄 인덱스(상시) ③실제 내용(온디맨드).
  - status.md도 계속 자라면 같은 문제가 재발하므로 최대 줄 수 상한 + 초과분은 별도 파일로 밀어내고 인덱스에 한 줄만 남기는 로테이션 필요.
  - 자사(헤르메스) 사례: 메모리 인덱스가 54줄로 이미 비대화 조짐, 스킬 733개인 에이전트는 스킬 설명을 57자로 강제 절단해 온디맨드 원칙을 런타임 차원에서 강제하고 있음.
  - **실측 결과**: 위 방식(자동 로드에서 완전히 제외)을 적용한 P20은 "60~70% 정도 절감"되었다고 확인.

- **PiKVM + Android 다중 스마트폰 관리 실패 사례**: 여러 스마트폰을 PiKVM으로 관리하려 시도했으나, PiKVM으로 묶으면 ADB(USB) 디버거를 동시에 사용할 수 없는 구조적 충돌로 실패.

- **WOL(Wake-on-LAN) 개념**: 네트워크로 신호를 보내면 메인보드가 인식해 전원이 켜지는 원격 부팅 기술. 단, PC가 WOL을 지원해야 한다는 하드웨어 제약이 있음. 원격지 PC를 상시 대기(always-on) 별도 장치(NanoKVM/PiKVM)로 관리하고 VM/작업환경과 전원 관리를 분리하는 아키텍처가 제안됨.

- **기업 내 AI 자동화 도구 배포 시 보안 이슈**: exe 배포는 IT/보안팀이 내용물을 알 수 없어 민감하게 통제하는 반면, 크롬 익스텐션은 감시가 덜하고 배포·업데이트가 간편해 사내 소규모 자동화 도구로 선호됨(개발자 등록비 $5, ZIP+개발자모드보다 편함). 다만 AI가 로그인해 사내 데이터(인사정보 등)를 크롤링/정리하는 것은 "사람이 복사·붙여넣기"와 다른 리스크로 취급되어 회사가 공식적으로는 막는 경우가 많다는 논의 — 책임 소재 불분명, 취약점·기밀정보 검증 부재가 이유로 언급됨. AI 도입은 "top-down(책임자 승인)" 방식이 바람직하다는 의견.

- **오래된 웹 보안 기법(역사적 회고, 기술적 통찰 포함)**: 브라우저 개발자도구(F12)로 비활성화된 저장 버튼의 `disabled` 속성 제거해 강제 저장, `input type` 변경으로 자동저장된 비밀번호 평문 열람 가능 — "비밀번호 자동저장된 브라우저를 켜둔 채 자리 비우면 위험"이라는 보안 주의사항으로 이어짐. 옛 싸이월드/세이클럽 시절 XSS로 미니룸/채팅창/카페 게시판에 스크립트·`<marquee>` 삽입, URL의 `preview?id=`를 `view?id=`로 바꿔 유료 콘텐츠 접근 등 사례 공유.

## 자동화·시스템 적용 후보

- **다중 에이전트 수동 핸드오프 교차검증 워크플로**: 헤르메스에서 아이디어 도출 → 클로드코드가 기획 빈틈 검증 → 헤르메스가 정합성 재확인(GPT5.6) → 헤르메스가 작업 실행 → 클로드코드가 재교차검증. 자동화보다 오히려 수동 핸드오프(복붙)를 의도적으로 유지하는 이유는 "애들끼리 무슨 소리로 밑장 깔지 몰라서"라는 통제 목적.
- **증거 기반 검증 강제 패턴**: 에이전트의 답변을 그대로 믿지 않고 "팩트 찾아오라"고 재요구하거나, 여러 에이전트에게 같은 사안을 교차 질문("대질심문")해 모순을 잡아내는 방식. "실제 증거파일을 쓰고 검증했는지를 강제하는 게 중요"하며 "구멍이 있어도 계속 메꿀 수 있다"는 코멘트.
- **메모리/컨텍스트 3층 설계**: 상시(규칙, 짧은 인덱스) vs 온디맨드(본문 상세) 구조 + 자동 로드 파일에 최대 줄 수 상한과 로테이션(오래된 항목은 별도 파일로 밀어내고 인덱스에 한 줄만 유지) 적용.
- **상태 데이터(transcript)와 코드의 수명 분리**: VM 내부 데이터를 GCS 등 외부 영속 스토리지로 분리해 VM 재구축과 무관하게 이력 보존.
- **WOL + always-on 원격 KVM(NanoKVM/PiKVM) 조합**: 작업 환경(VM/PC)과 전원 관리 계층을 분리해 VM 장애 시에도 물리 PC 전원 제어가 가능하도록 하는 아키텍처.
- **크롬 익스텐션 기반 사내 업무 자동화 배포**: exe보다 설치·업데이트·관리가 쉽고 IT 감시를 우회하기 용이해 소규모 조용한 배포에 적합.

## 질문·미해결

- devbox VM의 높은 의존성/결합도 문제에 대한 근본 해법은 대화 참가자 대부분이 비개발자라 명확히 제시되지 못함. "비슷한 환경을 가진 선배님이 있는지" 질문에 대한 뚜렷한 답변은 나오지 않음.

맞습니다, 황금호랑이님. H3의 진짜 혁신은 화질보다 ‘영상·음향을 하나의 생성 과정으로 통합했다’는 점입니다.

MiniMax H3 핵심

- 텍스트·이미지·영상·음성을 함께 이해하는 33B 옴니모달 생성 모델
- 최대 2K·15초·24fps 영상과 네이티브 스테레오 음향 생성
- 대사·효과음·배경음악을 나중에 합성하는 것이 아니라, 동일한 디노이징 과정에서 영상과 함께 생성
- T2I, I2V, 편집, 피사체·모션·음성 참조 등을 별도 모델로 나누지 않고 하나로 통합
- H3-Base가 768p 영상·음향을 만들고, H3-Regenerate-2K가 자기 출력을 다시 생성해 2K로 고도화
- SGLang·vLLM·Diffusers·ComfyUI가 출시 초기부터 지원

왜 ‘혁명’에 가까운가

기존 영상 제작은 대체로 다음과 같았습니다.

영상 생성 → 음성 합성 → 효과음 → 음악 → 싱크 조정

H3는 이를 다음처럼 바꿉니다.

창작 의도 + 멀티모달 자료 → 영상·대사·효과음·음악 동시 생성

즉, 여러 생성 도구를 연결하는 워크플로우에서 하나의 통합 창작 모델로 중심이 이동합니다.  
이는 황금호랑이님의 myTok·TokBridge 관점과도 닮았습니다. 기능별 도구를 단순 연결하는 단계를 넘어, 여러 입력을 하나의 문맥으로 이해하고 결과 전체를 함께 생성하는 방향입니다.

가장 중요한 함정

한국에서는 공개 웨이트를 그대로 내려받아 운영하면 안 됩니다.

- H3 Community License의 적용 지역에서 대한민국·미국·EU·영국이 제외
- 다운로드 자체는 가능하지만, 기술적 접근 가능성과 법적 사용 허가는 별개
- 국내에서 웨이트를 배포·운영하려면 MiniMax의 별도 승인이 필요
- 현재 한국에서는 글로벌 API 사용이 현실적인 기본 경로

따라서 지금은 로컬 설치보다:

1. API로 품질·비용·한글 대사·음향 싱크 검증  
2. 콘텐츠 제작 파이프라인에 제한적으로 적용  
3. 라이선스 변경 또는 별도 승인 후 로컬 운영 검토  

순서가 안전합니다.

누리의 판단: 이것은 단순한 영상 모델 신제품이 아니라, 이미지·영상·음향을 나눠 처리하던 ‘모달리티별 도구 시대’가 끝나기 시작했다는 신호입니다. 다만 한국 사용자에게는 현재 오픈 웨이트 혁명이라기보다 API 기반 체험판 혁명에 가깝습니다.
