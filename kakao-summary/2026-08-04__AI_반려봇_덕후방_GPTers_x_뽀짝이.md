## 인사이트·노하우

- **OpenClaw로 엑셀 업무 자동화한 크롬 익스텐션 제작** (P7): 회사 엑셀 시트에 데이터 붙여넣는 작업을 OpenClaw에게 시켜 크롬 익스텐션으로 완성. 고정 데이터는 웹 크롤링으로 자동 붙여넣기 처리, 용량은 324kb. 데이터 자동수집 로직만 추가하면 "딸깍"으로 시트 정리 완성되는 수준.
- **리눅스 크론잡 기반 업무 자동화 = 토큰 비용 0** (P7): 세일/인벤토리/고객만족도 KPI 데이터 파싱 → 메일 발송, 노무 점검 등 매장 운영 업무를 리눅스 크론잡으로 돌려서 "토큰 사용량은 0"이라고 언급. 크론잡은 앤비디아 제공 무료 API 활용(P44).
- **사이트/앱 디자인은 기본 LLM만으로 부족** (P38): 별도 하네스나 스킬이 필요하고, 레퍼런스를 많이 먹이고 컴포넌트를 활용해야 결과물 품질이 올라감.
- **Slack vs Notion 자료 정리 특성 차이** (P4, P24): Slack은 협업에 강하지만 캔버스/리스트로는 자료 정리에 부족함(Notion 대비 인라인 DB 기능도 없음). Notion은 자료 정리(문서·PPT 등)에 더 적합. Slack에 연동한 Hermes에 Notion을 붙이는 조합도 언급(P35).
- **Hermes + Claude Code 이중 구조 운용법** (P38): Hermes나 OpenClaw에 Claude를 직접 붙이는 것은 비추천. 대신 Hermes가 있는 PC에서 Claude Code로 Hermes를 세팅하고, 실제 작업(워커)은 저렴한 모델에게 맡기는 방식을 권장. "헤르메스도 결국은 파일 단위"라 이 구조가 가능하다고 설명.
- **워커 모델 선택 기준** (P19): 워커는 "지시받은 내용으로 작성만 하는" 역할(코드·문서 작성)이므로, 창의성보다 "지시대로 잘 처리하는 모델"이 적합하다는 관점.
- **Opus5 vs GPT-5.6 sol 비교 의견**: GPT-5.6 sol은 사용자 의도 대비 AI 맥락이 클로드보다 아직 어긋나는 경우가 있어 비즈니스 용도로는 클로드가 낫다는 의견(P19). 다만 장기 에이전트 작업·편집 능력 면에서는 GPT-5.6 계열도 최상급이며, Opus5는 문서 표현/정교한 재구성에서 여전히 선호될 수 있다는 정리 답변 인용됨. Hermes에서 Opus5를 기술적으로 쓸 수는 있으나 Claude 구독 기본량이 아니라 API나 추가 크레딧이 필요할 수 있음.
- **하네스 없이 쓰는 방식** (P7): "너가 하고 싶은데로 다해"라는 방침으로 별도 하네스를 두지 않음. 모델이 똑똑해질수록 하네스 자체가 필요 없어진다는 견해.
- **OpenClaw 스킬 자동저장의 함정** (P47): 반복 작업 중 "하면 안 되는 내용"이 명확히 규정되지 않으면 스킬이 스스로 와전(왜곡)되는 문제가 있음.
- **OpenClaw vs Hermes 선택 기준 요약** (P38): "내가 코딩이나 산출물을 만들어낼거다, 멀티 오케스트레이션이 필요하다 → 헤르메스 / 빠르고 쉽고 개인비서 용도로 쓸거다 → 오픈클로 / 둘다 별로다 커스터마이징 할거다 → 파이 에이전트 +@". 결국 "하나의 두꺼운 하네스"라는 개념이라 절대적 우위는 없다는 결론.
- **OpenClaw의 구조적 특징** (P34, P18): soul.md 비중이 큰 철학, 폴더 구조가 직관적이고 가볍게 구동됨. 파일 우선순위가 고정적이고 명확해서 복잡도 낮은 작업은 빠르게 처리.
- **OpenClaw에 적합한 작업 유형** (P3): 스스로 진화·변화하면 안 되고 정해진 틀 안에서만 작업해야 하는, 틀을 벗어나면 위험한 종류의 작업.
- **Hermes도 자기진화 제어 가능** (P18): Hermes 역시 자가진화 기능을 끄거나 휴먼게이트로 설정할 수 있음(참고용 반론).
- **Codex vs OpenClaw 사용 경험** (P7): OpenClaw에는 모든 권한을 줘서 편하게 쓰는 반면, Codex는 계속 승인이 필요하고 맥락도 새로 잡아야 해서 불편함. 다만 "코덱스 버전이 오를 때마다 일 잘하는 게 느껴진다"는 긍정적 변화도 언급.
