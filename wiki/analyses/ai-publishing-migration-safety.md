# AI 게시 파이프라인의 안전한 이관과 발행 이력 관리

OSS Radar와 Research Wiki 이관에서 반복 확인된 원칙이다. 분석 성공·인증 성공·예약 실행 성공을 실제 게시 성공과 구별하고, 상태 이력과 게시자를 함께 전환한다. 도메인 핵심 운영 결정이며 두 파이프라인에서 재현돼 범용 분석으로 수집한다.

## 핵심 내용

- 후보 선정 때 history를 쓰면 분석·게시 실패 자료까지 처리된 것으로 제외된다. Wiki push 성공 이후 이력을 갱신한다. OSS Radar는 700→600개, Research Wiki는 390→362개로 실제 게시 결과에 맞춰 백업 후 복구했다. 이력은 clone으로 따라오지 않는 운영 상태이므로 체크섬으로 이관을 확인한다.
- 전체 dry-run은 수집·변환·분석·페이지 검증을 수행하되 원격 Wiki와 history를 변경하지 않는다. GitHub API 조회 인증과 Wiki 쓰기 인증은 별도 확인한다. push dry-run 성공은 실제 게시 성공의 증거로 대신 쓰지 않는다.
- 새 서버 예약은 비활성으로 준비한다. 마지막 기존 실행을 확인하고 최신 history를 동기화한 뒤 기존 예약 중지→새 예약 활성화로 게시자 하나만 유지한다. 첫 정기 실제 게시와 원격 commit·이력 증가를 확인한 뒤 다음 프로젝트를 통합한다.
- 서버 UTC와 게시 날짜 KST를 구분한다. 파일명뿐 아니라 생성 시각과 Home 링크까지 같은 날짜 기준을 사용한다.

## 서비스 계정과 장애 관측

외부 콘텐츠를 AI CLI로 처리하고 GitHub 쓰기 권한을 갖는 작업은 서비스 계정으로 운영했다. 성격이 같은 게시 작업은 공용 계정으로 통합하되 프로젝트 간 격리가 줄어드는 점을 감수한다. 계정 홈을 옮길 때 UID/GID 유지와 별개로 CLI의 절대경로 symlink·인증·systemd 실행 계정을 확인한다. symlink는 release→current→실행 링크의 의존 순서로 복구한다.

OSS Radar에서는 모델 설정이 비어 기본 모델을 사용하는 구버전 CLI가 새 기본 모델을 지원하지 못해 분석 전체가 실패했다. 같은 구버전 호출로 재현했으며 stderr 첫 200자만 저장하던 로그가 오류 본문을 숨겼다. 마지막 4,000자를 보존하도록 개선하고 실제 응답·전체 dry-run으로 복구를 검증했다. 단순 버전 업데이트보다 모델 지원과 오류 본문 확인이 핵심이다.

서비스 exit 0만으로 게시 상태를 판단하지 않는다. 토픽별 성공·후보 없음에 따른 정상 생략·실패, 실제 원격 게시를 구분한다. 디스크 감소도 게시물과 CLI 설치본·캐시 증가를 분리해 조사한다. 이전 CLI 버전의 자동 정리 정책은 세션에서 확인하지 못했으므로 자동 삭제를 보장하지 않는다.

## 관련 맥락

구체적인 OCI 이관·공용 계정 적용은 [[oss-radar]]와 [[dev-blog]], 환경파일과 서비스 인증 분리는 [[launchd-secret-management]]를 참조한다. 이 문서는 세션에 기록된 결과를 정리하며 현재 서버를 재검증하지 않았다.

## 정기 실행 증거와 수집 소스의 부분 실패

정기 게시 검증은 토픽 실행 시각을 해당 서비스 실행 구간과 대조한다. 이후 수동 실행의 성공으로 앞선 정기 실패를 덮지 않는다. oneshot의 완료 후 inactive는 정상이며 종료 시각은 `ExecMainExitTimestamp` 또는 journal로 판단한다. 최신 상태 스냅샷만으로 과거 날짜의 성공을 증명하지 않는다. Pages 빌드 성공도 모든 토픽의 게시 성공을 대신하지 않는다.

Research Wiki의 반복 429 조사에서는 API 키 없는 Semantic Scholar 호출이 익명 공유 한도의 영향을 받으며, 현재 코드는 재시도 없이 경고와 빈 후보 목록으로 넘어간다고 기록됐다. Hugging Face 대체 후보로 게시할 수 있어도 Semantic Scholar 후보·인용 점수가 빠지므로 **게시 가용성과 수집·선정 품질을 별도로 보고**한다. 정상 후보 없음과 소스 호출 실패를 같은 생략으로 취급하지 않는다.

API 키 등록과 제한적인 대기·재시도는 조사 후 제안이며 적용되지 않았다. 키가 선택 사항이라는 초기 설명은 실행 가능성을 뜻할 뿐 안정적인 수집을 보장하지 않는다. API 정책과 서버 상태는 세션 당시 확인 내용이며 이번 수집에서는 재조회하지 않았다.

## 이관 검증은 셸과 AI CLI 실행 환경까지 포함한다

Research Wiki의 마지막 Mac 정기 실행은 수집·분석 이후 게시 호출 직전에 실패했다. 세션에서 재현한 원인은 macOS Bash 3.2의 `set -u` 아래 빈 `${PUBLISH_ARGS[@]}` 확장이었다. OCI의 최신 Bash에서는 통과해 서버 dry-run만으로 발견되지 않았다. 빈 배열 확장을 사용하지 않는 분기로 수정하고 일반 게시·dry-run 회귀 테스트를 추가했으며, 이미 생성된 분석을 보존한 채 `publish.py`만 실행해 게시와 history를 복구했다(보고 커밋 `d4ee3b3`). 컷오버 전까지 살아 있는 기존 실행 환경도 검증 대상이다.

같은 세션 후반 news-monitor에서는 OCI Cursor의 강제 샌드박스 초기화가 실패했고, 후속 커널 로그에서 AppArmor의 사용자 네임스페이스 거부를 확인했다고 보고했다. 전역 보안 설정이나 예외는 변경하지 않았다. 이후 Mac의 읽기 전용 Codex 호출로 실제 분류가 성공했으나, 이것은 OCI Cursor 복구나 운영 배포 성공의 증거가 아니다. 로그인·단위 테스트 통과와 실제 CLI의 실행 격리 환경 검증을 구별한다. 구체적인 CLI 옵션·OS 정책의 현재 호환성은 이번 수집에서 재확인하지 않았다.

## 호출 제한과 이전 정상 데이터는 실행을 넘어 추적한다

news-monitor의 반복 429 대응에서는 재실행해도 최소 15분간 요청하지 않도록 대기 상태를 보존하고 동시 실행을 차단했다. 마지막 재시도 응답의 서버 대기 시간도 놓치지 않도록 수정했다고 보고했다. 15분은 이 구현의 선택값이며 모든 API의 공통 정책이 아니다. 설정 오류에서도 과거 성공 상태가 남지 않게 했고, 테스트 통과와 실제 소스 수집 성공을 따로 기록했다.

후속 수집 실패로 기존 정상 결과를 빈 데이터로 덮지 않고, 이전 수집 시각과 실패 경고를 표시했다. 이전 데이터를 제공할 수 있다는 사실을 새 수집 성공으로 집계하지 않는다. 이 원칙은 앞선 Research Wiki의 대체 소스 게시와 함께 가용성·신선도·수집 범위를 분리하는 반복 사례다. 자동 분류의 보류·통계 표시 경계는 [[llm-content-quality-guards]]를 참조한다.
