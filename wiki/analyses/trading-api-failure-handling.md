# 트레이딩 API 실패: 복구·영향·수정 필요성 구분

외부 API의 HTTP 500 발생 횟수만으로 코드 수정 과제를 만들지 않는다. 복구 여부와 실제 매매 영향을 구분하고, 조회 실패 시 오래된 계좌 정보를 최신값처럼 사용하는 결함을 먼저 막는다.

## 핵심 내용

1. 재시도 후 정상 복구되고 매매 영향이 없으면 일시 오류로 집계한다.
2. 실패가 지속돼 잔고 확인·매매 감시에 영향을 주면 운영 장애로 알린다.
3. 요청 방식이나 오류 처리의 내부 결함이 확인됐을 때 코드 수정으로 연결한다.

반복 500이 공급자 문제일 가능성은 있지만 상태 코드만으로 원인을 확정하지 않는다. ht_trading의 10/15 장외 잔고 조회 8회는 모두 성공해 원인이 미확정이었다. 안전 처리 보완을 500 자체의 해결로 기록하지 않는다. 다음 조사도 실패 시 진단 코드와 복구·영향 증거를 기준으로 수행한다.

## 계좌 정보의 신선도와 거래 허용

같은 사이클의 계좌 갱신은 한 번의 최신 잔고로 일관되게 구성한다. 잔고 조회 실패 시 이전 캐시를 최신 상태로 취급하지 않는다. 주문가능금액만 실패한 경우 최신 보유 정보로 매도 감시는 유지하되 신규·추가매수는 보류한다. 모든 계좌 조회가 실패한 경우까지 정상 매도 가능하다고 확대 해석하지 않는다.

오류 진단에는 필요한 원인 코드만 남기고 계좌·토큰·응답 원문을 기록하지 않는다. 이 안전 처리는 `a06f4ca`로 반영됐다는 세션 보고다.

## 감지와 보고 정책의 차이

해당 세션의 코드 확인 보고에서는 재시도 중인 500도 경고 로그로 남겼지만, 텔레그램 API 중지 알림은 연속 실패로 주문 차단 상태에 들어갈 때 전송했다. 최종 판단은 회복·영향 중심 보고와 중복 알림 억제이며, 이 판단을 정리하는 단계에서 운영 코드를 추가 변경하지 않았다. 향후 개선 제안을 이미 구현된 정책으로 기록하지 않는다.

5월 서킷브레이커와 10월 후속 수정에서 같은 신선도·실패 판단 문제가 반복돼 범용 분석으로 정리했다. 직접 출처는 단일 세션이며 외부 장애 원인이나 모든 API의 보장으로 일반화하지 않는다.

## 주문 전 보류 사유를 안전하게 관측하기

주문이 없을 때는 정상적인 조건 미충족과 조회 실패·내부 검증 실패를 구분할 수 있어야 한다. 내부 검증 사유와 검증 위치, VI/거래정지 상태처럼 필요한 구조화 정보만 남기고, URL·토큰·계좌번호가 섞일 수 있는 예외 원문은 출력하지 않는다. 단순히 예외 전체를 추가 로깅하는 방식은 진단 개선과 비밀정보 노출을 함께 일으킬 수 있다.

10/20 양지사·야스의 주문 전 보류는 상세 로그가 없어 원인을 확정하지 못했다. 후속 `d21f739`는 정책 지문으로 보호되는 매매 로직 대신 로깅 계층에서 사유를 표시했다는 세션 보고다. 시세·자금·소유권 검증 위치와 VI·보유 한도·주문 시간 초과 등을 구분하며, 비밀값 포함 예외의 비노출 및 주문 상태·예약금 회귀 검증이 보고됐다.

국내 엔진만 정상 재시작한 뒤 기존 주문·체결·현금 풀·6개 보유의 수량/소유권과 정책 지문 보존을 확인했다고 보고했다(전체 968개·서브테스트 13개). 이는 이후 보류의 관측 가능성을 보강한 것이며, 과거 두 종목의 원인을 소급 복원한 결과가 아니다. 이번 수집에서는 코드를 실행하거나 서비스를 재시작하지 않았다.

## 접수 미확인 주문은 조회 실패와 다른 복구 문제다 (10/21 후속)

10/21 09:48 KST 세션 보고에서는 09:35 첫 매수 이후 다음 주문이 KIS 호출 한도 초과 응답을 받고 접수 미확인 상태로 남았다. 이후 역행 후보와 기존 전략의 신규매수가 중복 주문 방지를 위해 보류됐고, 기존 보유의 매도 감시는 계속됐다. 프로세스 가동·매도 감시와 신규매수 가능 여부를 따로 보고해야 하는 실운영 사례다.

공식 주문을 두 번 조회했지만 해당 주문은 확인되지 않았다. 이 보고를 **미접수 확정이나 전량 거부로 바꾸어 기록하지 않는다**. 접수 미확인 상태는 [[kis-fully-rejected-order-status]]의 확인된 전량 거부와 다르며, 비멱등 주문을 곧바로 다시 보내면 [[order-post-retry-double-fill]]의 중복 접수 위험이 있다. 예약금 해제·재주문에 앞서 접수 여부와 로컬 상태를 대사하는 복구가 필요하다.

현금 부족은 아니며 재시작만으로 해결되지 않는다고 보고됐다. 세션은 조회로 끝났고 임의 예약금 해제·재주문·호출 제한 처리 수정은 수행하지 않았다. 안전 차단이 동작한다는 사실과 신규매수 장애가 복구됐다는 사실을 구별한다. 호출 제한 응답의 상세 코드·안전한 자동 복구 구현·후속 체결 결과는 출처에서 확인되지 않았다.

## 10/21 장마감~10/22 후속: 거부 증거 기반 복구와 호출 제어

위의 ‘미복구·상세 코드 미확인’은 오전 조사 시점의 이력이다. 후속 세션은 `EGW00201` 호출 제한 응답을 접수 미확인으로 저장한 뒤, 주문번호가 없어 자동 대사·120초 잔량 취소로 해소하지 못했다고 보고했다. 복제 장부에서 다음 날에도 신규매수가 차단되는 것을 재현했다. 단순 재시작은 영속 주문 상태의 복구가 아니다.

최종 구현은 **접수 전 거부가 확인되는 주문과 실제 응답 유실을 구분**한다. 정확한 거부 로그·공식 주문 두 번 조회·보유 수량 대사가 모두 일치할 때만 복구 도구로 거부 확정 처리한다. 주문 조회에 없다는 사실 하나나 HTTP 500만으로 예약금을 해제하거나 자동 재주문하지 않는다. 진짜 접수 불명 상태는 예약금과 중복 주문 보호를 유지한다.

호출 증가 경로도 모의 재현됐다. 120초 전략 판단 여부를 확인하기 전에 15초 틱마다 주문·잔고·현금을 3회 조회했고, 종목별 주문 준비에서 계좌 확인·현재가·해시 발급 등 약 6회가 추가됐다. 신규매수 차단 후 남은 6개 계획도 계좌 재조회 18회를 수행했다. **18회는 최초 오류 이후의 모의 재현값이며 당시 하루 총호출 수나 초당 실측값이 아니다.**

후속 수정은 판단 주기·차단 상태를 먼저 확인해 중복 조회를 줄이고, 실거래·페이퍼·수집기가 같은 호출 제한 장부를 사용하며 실주문에 우선순위를 두도록 했다([[shared-broker-appkey-token-cache]]). 프로세스별 호출 간격만으로 공유 자격증명의 합산 부하를 제어했다고 보지 않는다.

장외 복구·재시작 뒤 예약금 0원·신규매수 차단 사유 0개·보유 5종목 일치와 보호 대상 6개 테이블 보존이 보고됐다. 놓친 과거 후보는 재주문하지 않았다. 국내 매매 1,008개·대시보드 391개·수집기 251개 테스트 및 최종 합계 1,651개 통과는 세션 보고다. 항목별 합계는 1,650개로 최종 보고와 1개 차이가 있어, 이번 수집에서는 이를 독립 검증한 정확한 총수로 확정하지 않는다.

~~세션 말미의 정확한 한도·당시 총호출 수·밴 여부 질문은 조사 착수에서 끝났다.~~ 이후 답변이 추가됐으며 아래 후속 확인을 따른다. 초당 전체 요청 기록이 없어 어느 프로그램이 초과분을 만들었는지 확정할 수 없으며, 호출 제한 응답을 계정 밴으로 단정하지 않는다. 다음 정상 진입창의 실제 체결 대조도 아직 확인 전이다.

## 10/22 후속 확인: 호출 제한 응답과 계정 밴을 구분한다

추가 답변에서는 10/21 09:35:49 주문의 호출 제한 응답 1건이 로그에서 확인됐고, 이후 조회·매도는 계속돼 계정 전체 밴의 증거는 없다고 보고했다. 하루 신규매수 중단은 그 응답 뒤 로컬 미확인 주문이 영속 차단을 유지한 결과다. 로그의 오류 1건은 전체 계좌 호출량을 측정한 값이 아니다. 당시 모든 요청을 집계하지 않아 정확한 초당/당일 총호출 수와 어느 프로그램이 초과분을 만들었는지는 여전히 미확정이다.

공식 공지를 확인했다는 세션 보고는 일반 실전 한도를 계좌당 초당 18회, 적용한 내부 제어를 합산 초당 8회·배경 조회 최대 4회로 설명했다. 과거 약 20회·appkey 단위 설명과의 시점/범위 차이, 공지 출처와 검증 경계는 [[shared-broker-appkey-token-cache]]에 통합한다. 호출 집계도 시작됐다고 보고했으며 이로부터 과거 미수집 호출량을 소급 산출하지 않는다.
